# Техническая архитектура

Версия 2: без n8n, свой код + собственная CRM. Решения зафиксированы: OpenRouter как LLM-провайдер, боты в Telegram и MAX, кабинет владельца и админка на своём домене.

## Принципы

1. **Один сервис, одна база.** Никаких конструкторов: боты, планировщик, кабинет и админка — один репозиторий, одна Postgres, один docker-compose на VPS.
2. **Postgres — источник правды.** Все сущности в БД с `salon_id` в каждой строке (мультитенантность). Кабинет, боты и воркер читают/пишут одно и то же.
3. **Онбординг салона = запись в базе.** Новый клиент заводится формой в админке за минуты, ничего не копируется руками.
4. **Надёжность и безопасность как фича** (зона ИБ-партнёра): изоляция тенантов, бэкапы, мониторинг, «данные в РФ».

## Схема

```
Клиент салона                                Владелец салона / мы
  │  Telegram / MAX / SMS                        │  браузер (HTTPS)
  ▼                                              ▼
┌────────────────────── VPS (РФ), docker-compose ──────────────────────┐
│                                                                      │
│  Caddy (HTTPS, reverse proxy, сертификат Let's Encrypt)              │
│    ├── /webhook/tg/<salon>  ─┐                                       │
│    ├── /webhook/max/<salon> ─┤                                       │
│    └── app.домен.ru ─────────┼──► Веб-приложение (кабинет + админка) │
│                              ▼                                       │
│  Backend-сервис (FastAPI или Node — одна кодовая база):              │
│    • bot handlers  — диалоги записи, кнопки, FAQ                     │
│    • scheduler/worker — каскад напоминаний, реактивация, отчёты      │
│    • API кабинета  — REST для фронта                                 │
│                              │                                       │
│  PostgreSQL ◄────────────────┘      Uptime Kuma (мониторинг)         │
└──────────┬────────────────────────────────┬──────────────────────────┘
           ▼                                ▼
   Внешние API: SMS-агрегатор,      Бэкапы: ночной дамп БД → S3 (РФ)
   OpenRouter (LLM), YCLIENTS
   (синхронизация, где есть)
```

## Компоненты

### Backend-сервис (одна кодовая база, три роли процессов)

- **Bot handlers.** Telegram — aiogram (Python) или grammY (Node); MAX — HTTP к `platform-api2.max.ru` (API в стиле Telegram, для Python есть maxapi в духе aiogram). Диалог записи — конечный автомат: выбор из списков едет в `callback_data` кнопок, свободный ввод (имя, телефон) — через таблицу состояний `dialog_state`.
- **Worker (планировщик).** APScheduler/Celery beat. Задачи: каждые 15 мин — выборка визитов для напоминаний (T−24 ч и T−2…3 ч), догоны, лист ожидания; ежедневно — реактивация; ежемесячно — отчёты. Вся логика каскада — SQL-выборки по `bookings` + `message_log`.
- **API кабинета.** REST/JSON для фронта, роли `owner` (видит свой салон) и `superadmin` (видит всё).

### Каналы сообщений и каскад

Приоритет каналов задаётся в конфиге салона; у клиента салона храним `tg_id` и/или `max_id`.

1. Напоминание уходит в приоритетный бесплатный канал (Telegram или MAX).
2. Не подтвердил кнопкой за 2–3 ч → второй бесплатный канал, если известен.
3. Не подтвердил → SMS через агрегатора (SMS Aero / SMSC / SMS.ru, HTTP API, 3–6 ₽/шт).
4. Клиенты без мессенджеров (записаны по телефону) — сразу SMS.

Важно: каскад строится на «не подтвердил», а не «не прочитал» — read-статусов у бот-API нет. Бот не может написать первым тому, кто не запускал бота → холодная база реактивируется SMS-волнами со ссылкой на бота (порциями, с фильтром «не беспокоили 60 дней» и кнопкой отписки), перетекая в бесплатные каналы.

MAX: токен через @MasterBot, вебхуки на наш HTTPS, лимит 30 rps, на сервере — сертификат Минцифры в доверенных. Публикация бота — с верификацией; самозанятости достаточно.

### Веб-приложение (кабинет + админка)

Один фронт, две роли:

- **Кабинет владельца:** дашборд (визиты, % подтверждений, предотвращённые неявки, «возвращено ≈ N ₽» за месяц), журнал записей со статусами и ручным добавлением (телефонные записи попадают в тот же каскад), база клиентов со «спящими» и исключением из рассылок, настройки услуг/циклов/текстов/часов, архив отчётов.
- **Админка (мы):** список салонов со статусом и здоровьем, онбординг-форма (создаёт салон, регистрирует вебхуки ботов), расход SMS против лимитов, биллинг абонентки, логи сообщений и ошибок, feature-флаги по салонам.

Стек: Next.js либо FastAPI + React (что удобнее по вайбкодингу), деплой за Caddy на том же VPS.

### LLM-слой (OpenRouter)

- ИИ-ассистент бота (`app/bots/assistant.py`, флаг салона `llm_assistant`): клиент пишет обычным текстом («к Лене в четверг после 6 на маникюр»), LLM разбирает фразу в намерение (записаться / перенести / отменить / вопрос) и поля (услуга, мастер, дата, окно времени). Дальше всё детерминированно: слоты считает `services/slots.py`, запись создаёт тот же код, что и у кнопок. Не хватает данных — один уточняющий вопрос, кнопки остаются запасным путём. Отмена всегда подтверждается.
- LLM выбирает только из того, что есть в салоне: id услуг и мастеров, даты в пределах горизонта. Всё прочее из ответа модели отбрасывается.
- Жёсткое требование (т.к. запросы уходят на зарубежную инфраструктуру): имя, телефон, история визитов из Postgres в промпт не попадают никогда. Промпт собирается из данных салона (услуги, цены, мастера, часы, поле «О салоне»); единственная переменная — текст клиента, из которого до отправки вырезаются телефон, email и «меня зовут …» (они разбираются локально). Имя из профиля и Telegram не отправляется.
- Неуверенный ответ на вопрос → клиенту «уточню у администратора», админу — тикет в мессенджер. LLM недоступна → обычное меню с кнопками.
- Провайдер — любой OpenAI-совместимый endpoint (`LLM_BASE_URL`, `LLM_MODEL`); по умолчанию OpenRouter. Если OpenRouter недоступен из РФ-сервера, подставляется российский шлюз с тем же API без правок кода.
- Питч остаётся честным: «данные клиентов хранятся в РФ и не передаются во внешние сервисы».

### Интеграция с YCLIENTS (где она есть у салона)

Двусторонняя синхронизация записей YCLIENTS ⇄ наш Postgres отдельной задачей воркера. Кабинет всегда показывает нашу базу. Проверять доступность API на тарифе салона ДО обещания интеграции.

## Безопасность (зона ИБ-партнёра)

- VPS и данные — в РФ; Caddy + Let's Encrypt, всё за HTTPS.
- Мультитенантная изоляция: проверка `salon_id` в каждом запросе API и каждом SQL — главная поверхность атаки таких систем.
- Auth кабинета: argon2/bcrypt, сессии, rate-limit на логин, аудит-лог действий в админке.
- Секреты (токены ботов, ключи SMS/LLM) — в env/секрет-хранилище, не в коде; ротация при офбординге салона.
- Минимизация ПДн: имя, контакт, история визитов — ничего лишнего; в LLM ПДн не уходят.
- Бэкапы: ночной дамп Postgres → объектное хранилище РФ (S3 Timeweb/Selectel, ~50 ₽/мес), проверка восстановления раз в месяц.
- Мониторинг: Uptime Kuma на healthcheck-эндпоинты сервиса и вебхуков; алерты нам в мессенджер — чиним раньше, чем заметит салон.

## Онбординг салона (цель ≤ 15 минут)

1. Создать ботов у @BotFather (TG) и @MasterBot (MAX), получить токены.
2. В админке: форма «новый салон» — название, токены, средний чек, часы работы.
3. Система регистрирует вебхуки, создаёт дефолтные тексты и услуги-заготовки.
4. Владелец (или мы) заполняет услуги и циклы в кабинете.
5. Тестовая запись + тестовое напоминание → салон активен, добавлен в мониторинг.

## Стартовая инфраструктура и затраты

VPS РФ 1–2 vCPU/2 ГБ (300–600 ₽/мес) · домен (~300 ₽/год) · баланс SMS (от 1 000 ₽) · S3 для бэкапов (~50 ₽/мес) · OpenRouter (по факту, копейки на FAQ). Итого старт ≈ 2–3 тыс. ₽.
