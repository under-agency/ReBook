# Карта кода CRM и что осталось сделать

Дополнение к 03-architecture.md и 10-crm-logic.md: где что лежит в коде,
какие места несут главную нагрузку и что ещё не реализовано.

Состояние на 29.08.2026: ~6 400 строк, 37 тестов проходят.
Кабинет владельца, админка, бот записи и каскад напоминаний работают.

## Ядро: восемь файлов, которые надо понимать

Если возвращаться к проекту после перерыва — читать в этом порядке.

| Файл | Строк | Зачем он главный |
|---|---|---|
| `apps/backend/app/models.py` | 257 | Вся схема БД. Любая новая фича начинается здесь. Статусы записей и салонов заданы константами вверху файла — они же используются в проверках. |
| `apps/backend/app/deps.py` | 64 | Главная поверхность безопасности: `salon_id` берётся из сессии, `get_owned_or_404` — единственный способ достать чужой объект. Ни один роут не должен читать `salon_id` из параметров запроса. |
| `apps/backend/app/services/bookings.py` | 141 | Ядро CRM-логики: создание записи с проверкой конфликтов, матрица статусных переходов, перенос, автозакрытие. Бот и API вызывают одни и те же функции. |
| `apps/backend/app/services/slots.py` | 72 | Свободные окна. Чистые функции без БД — поэтому тестируются напрямую и переиспользуются ботом, формой записи и переносом. |
| `apps/backend/app/channels.py` | 138 | Единственная точка отправки сообщений. Здесь каскад каналов, гейт по статусу салона, `do_not_disturb`, лимит SMS и запись в `message_log`. Нигде больше сообщения слать нельзя, иначе отчёты перестанут сходиться. |
| `apps/backend/app/worker/reminders.py` | 79 | Каскад T−24 / T−3 и автозакрытие. Главная ценность продукта для клиента. |
| `apps/backend/app/reports.py` | 109 | Формула «возвращено ≈ N ₽». Показывается владельцу открыто, поэтому менять её можно только осознанно. |
| `apps/backend/app/bots/dialogs.py` | 403 | Автомат записи, канал-агностичный. `telegram.py` — тонкий адаптер: если появится MAX, дублировать надо только адаптер. |

Фронт держится на `apps/web/src/App.tsx` (роутинг и гварды по ролям) и
`apps/web/src/components/editors.tsx` (редакторы услуг, мастеров, часов и текстов —
переиспользуются в настройках и в онбординг-мастере).

## Инварианты, которые нельзя нарушать

1. **`salon_id` только из сессии.** Чужой объект — 404, не 403. Тест
   `tests/test_tenant_isolation.py` обязан оставаться зелёным.
2. **Все сообщения — через `channels.send()`.** Прямые вызовы Telegram API мимо него
   ломают журнал сообщений, лимиты SMS и отчёт.
3. **Время в БД — только `timestamptz` в UTC.** Конвертация в пояс салона — на границах:
   расчёт слотов, отображение, границы месяца в отчёте.
4. **Статусы `reminded_*` ставит только система** (`set_status(..., by_system=True)`).
   Владелец выставляет вручную только итоговые статусы.
5. **Деньги — `Decimal`/`numeric`,** никаких `float` в расчётах.

## Что осталось сделать

### Блокеры продакшена

- [ ] **SMS-агрегатор.** Сейчас SMS-звено каскада пишется в `message_log` с
  `delivery_status='stub'`. Нужно: реализовать реальную отправку в `channels.py`
  (заменить ветку `if channel == "sms"`), добавить `app/sms.py` с HTTP-клиентом
  агрегатора (SMS Aero / SMSC / SMS.ru) и эндпоинт колбэка статусов доставки,
  который обновляет `delivery_status` по `message_log.id`.
- [ ] **Деплой.** VPS в РФ, `docker-compose` (postgres, backend, worker, web, caddy),
  Caddyfile с HTTPS и роутингом `/webhook/*`. Сейчас всё запускается локально
  тремя процессами через `scripts/dev.ps1`.
- [ ] **Вебхуки вместо полинга.** Локально бот работает полингом (`app/run_bot.py`).
  В проде нужен `POST /webhook/tg/<salon_id>` в `api/`, который отдаёт апдейт в
  `bots/dialogs.py`, и регистрация вебхука при онбординге салона в админке
  (сейчас админка сохраняет токен, но вебхук не ставит).
- [ ] **Отправка приглашений на email.** Сейчас ссылка-приглашение возвращается
  в ответе API и показывается superadmin — он копирует её руками. Нужен SMTP.
- [ ] **Бэкапы и мониторинг.** Ночной `pg_dump` → S3 РФ, Uptime Kuma на healthcheck.

### Функциональность из доков

- [ ] **Реактивация «спящих».** Вычисляемый статус клиента, фильтр и отписка уже есть;
  нет самой рассылки. Нужен `app/worker/reactivation.py`: выборка спящих по циклу
  услуги, фильтр «не беспокоили 60 дней» (`customers.last_outreach_at`), отправка
  порциями через `channels.send(kind="reactivation")`. Отчёт такие визиты уже считает.
- [ ] **Лист ожидания.** Таблица `waitlist` создана, логики нет. Нужно: предложение
  встать в лист, когда нет свободных окон (в `bots/dialogs.py` есть точка, где
  возвращается «свободных окон нет»), и рассылка предложения при отмене записи —
  первый нажавший забирает слот. Отчёт уже умеет считать `waitlist_offer`.
- [ ] **Напоминание T−3 в мессенджер.** Сейчас второе касание всегда уходит в SMS.
  По докам логичнее: второй бесплатный канал, если известен, и только потом SMS.
- [ ] **MAX-бот.** Адаптер `app/bots/max.py` по образцу `telegram.py`, канал `max`
  в `channels.py` (сейчас пропускается), сертификат Минцифры на сервере.
- [ ] **LLM-слой (FAQ).** Сейчас вопрос клиента уходит админу в чат уведомлением.
  Нужен `app/llm.py`: OpenRouter, база знаний салона, порог уверенности.
  Жёсткое требование из 03-architecture.md — ПДн в промпт не попадают.
- [ ] **Синхронизация YCLIENTS** для салонов, где она есть.
- [ ] **Серверный PDF отчёта.** Сейчас печать из браузера (`window.print()` + print CSS).

## Как продолжить работу

```bash
powershell -File scripts/dev.ps1     # Postgres в WSL + бэкенд + фронт + бот
cd apps/backend && python -m pytest  # 37 тестов
```

Схему меняем через Alembic: правим `app/models.py`, затем
`python -m alembic revision --autogenerate -m "что изменили"` и `alembic upgrade head`.

Демо-данные пересоздаются `python -m app.seed --reset`.
